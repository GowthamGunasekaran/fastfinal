# National One-Pager FastAPI - Layered V1

This project keeps the same functional behavior as the previous implementation,
but reorganizes it into API, DB, model, repository, schema, service, and utility layers.

## Structure

```text
app/
├── main.py
├── api/
│   └── v1/
│       ├── __init__.py
│       └── router.py                 # ALL V1 routes are registered here
├── db/
│   ├── __init__.py
│   ├── database.py                   # SQLite / SQLAlchemy connection
│   └── models/
│       ├── __init__.py
│       ├── pager.py                  # Pager table
│       └── pager_pillar_initiative.py# Pager/Pillar/Initiative table
├── models/
│   ├── __init__.py
│   ├── pager_model.py                # SQLAlchemy model re-export/compatibility
│   └── pager_pillar_initiative_model.py
├── repositories/
│   ├── __init__.py
│   ├── pager_repository.py
│   └── pager_pillar_initiative_repository.py
├── schemas/
│   ├── __init__.py
│   ├── pager_schema.py
│   └── pager_pillar_initiative_schema.py
├── services/
│   ├── __init__.py
│   └── pager_service.py
└── utils/
    ├── __init__.py
    ├── constants.py
    └── validators.py
```

## Important architecture

- `api/v1/router.py`: routes only. Business logic is not placed here.
- `services/`: business rules and orchestration.
- `repositories/`: database CRUD/query operations.
- `db/models/`: one SQLAlchemy table model per file.
- `schemas/`: Pydantic request/response contracts.
- `utils/`: enums/constants and reusable validation.
- `db/database.py`: database engine/session/base.
- `main.py`: application startup and router registration only.

## Database

SQLite is used for local development.

On first startup, `pager.db` is created automatically.

## Run locally

### Windows

```powershell
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
uvicorn app.main:app --reload
```

### macOS/Linux

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload
```

Open:

```text
http://127.0.0.1:8000/docs
```

## API endpoints

```text
POST   /api/v1/pagers
PUT    /api/v1/pagers/{pager_id}
PATCH  /api/v1/pagers/{pager_id}/status

GET    /api/v1/pagers
GET    /api/v1/pagers/{pager_id}
GET    /api/v1/users/{user_id}/pagers

GET    /health
```

## Create behavior

A create request can contain:

- 1 to 5 pillars
- 0 to 3 initiatives per pillar
- 0 to 3 image URLs per initiative

Therefore a complete request can create:

```text
1 pager row
15 pager_pillar_initiative rows
45 image URLs maximum
```

A draft can contain only one initiative or one pillar and be completed later.

## Edit behavior

`PUT /api/v1/pagers/{pager_id}` supports:

- editing pager fields
- adding a pillar
- adding an initiative
- editing an existing initiative
- changing image URL arrays
- changing weights
- changing scoring mode
- changing status

Important: omitted initiatives are NOT deleted automatically. This prevents accidental data loss during partial edit operations.

## Status

Supported statuses:

```text
DRAFT
PUBLISHED
DELETED
ARCHIVED
```

For `PUBLISHED` + `WEIGHTED`:

- all 5 pillars are required
- pillar weights must total exactly 100

## User query

`GET /api/v1/users/{user_id}/pagers`

returns all pagers created by that user and status counts.

You can filter:

```text
GET /api/v1/users/user-123/pagers?status=DRAFT
```

## Notes about IDs

`pager_id` is generated by the database.

`pillar_id` and `initiative_id` are represented in the combined child table as logical IDs.
For this initial SQLite implementation, the application uses the pillar/initiative
numbers as stable logical IDs when creating new child records. The physical row
primary key is `pillar_initiative_id`.

This can be changed later if you decide that pillar/initiative IDs must be globally
unique independent of a Pager.
